## What the code proves

The producer runs **independently before** formal execution; the formal entry reads a preflight artifact rather than importing the producer ([formal runner](../../scripts/run_step9_63_v3_formal_execution.py), lines 155–199). It is therefore not a direct runtime import, but it is a trusted *evidence-producing dependency*: a wrong producer can create incompatible or unauditable evidence. The current generic producer has a revision-generic freeze check and exclusive artifact write, but its ID format `preflight-step9_63c-r11-<uuid>` ([generic producer](../../scripts/preflight_step9_63c_current_mac_local.py), lines 16–27, 151–207) fails the frozen consumer's `preflight-step9_63c_r5-<token>-<uuid>` grammar (formal runner lines 46–60). It also has no persistent invocation claim. The successful registry-aware producer is outside the r10 20-member list and hard-binds r10 authorization/attempt/namespace/freeze SHA and ID prefix ([r10 producer](../../scripts/preflight_step9_63c_r5c7_mac_local.py), lines 20–30, 115–121, 301–333). It reports `preflight_script_sha256` in the artifact (lines 435–499), but the frozen consumer currently does **not** check this field or consult the invocation registry (formal runner lines 46–103). Thus the observed r10 workflow had an explicit artifact path/hash gate, not an end-to-end consumer-enforced producer/registry provenance gate. The design must strengthen future r11 guards; it does not rewrite r10 history.

The existing registry is an append-only **runtime audit log**, not an immutable contract: the r10 producer requires one genesis, strict UTF-8/JSON/keys, unique IDs, a regular non-symlink file and a file lock ([r10 producer](../../scripts/preflight_step9_63c_r5c7_mac_local.py), lines 25–29, 128–179). `claim_new_preflight_invocation()` checks history and target, appends and fsyncs a claim **before** preflight work (lines 189–211), so a failure after claim leaves the ID permanently used even without an artifact. The registry's full SHA necessarily changes on each claim; it cannot be a fixed r11 freeze member. Freeze the schema/path validation *in code*, pin a version/genesis contract, and audit an exact prefix length/hash at claim time without freezing the entire mutable log. Future readers must parse the **full** log under a shared lock, require one matching claim, reject duplicates/malformed/truncated history, and verify the claimed prefix has not changed. Claims should bind ID, authorization, attempt, runner freeze SHA, producer path/SHA, target and timestamp; the exact schema is a future implementation contract, not current fact.

## Decision: A over B

Recommend **A**: place the new r11 producer code in the 20-member freeze, replacing the obsolete r10 preflight-wrapper row; keep a new versioned invocation registry outside the member list as append-only runtime state. This uses the runner's existing member-hash root of trust and makes producer code drift fail closed before a claim. However, freezing producer code **alone is insufficient**. The frozen formal consumer must additionally verify the current producer file against the r11 member SHA, the artifact's producer SHA, and exactly one versioned registry claim/prefix binding before transaction creation. This is an additional reviewed r11 frozen-member edit. An artifact's self-reported producer hash by itself is not cryptographic proof of execution; the protection here is combined file integrity, pre-claim log durability, exclusive artifact creation and consumer-side cross-checks under the local integrity threat model.

Option **B** can be safe only with a separate immutable producer manifest/path/SHA bound into future authorization **and** checked by the producer at invocation and the frozen consumer at execution. The current authorization/consumer contracts do not do that. B therefore adds a second trust root and independent drift/rotation lifecycle while still requiring consumer changes; it is not rejected merely because it is more work. [A/B comparison](step9_63c_r5c10h_ab_decision.json) records the precise tradeoff.
